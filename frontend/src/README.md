# Frontend structure

- `app/` owns bootstrap composition, the global theme, and top-level navigation.
- `features/<domain>/` owns domain state, backend adapters, components, and hooks.
- `features/config/` owns persisted application settings; `features/settings/`
  is the settings screen that consumes them.
- `shared/` contains domain-independent layout primitives and utilities only.
- `i18n/` owns translation setup, locale metadata, resource files, and
  generated translation data. Feature-specific translation loaders stay in
  their owning feature directories.
- `data/` contains generated game catalogs. `bindings/` is generated by Wails;
  neither should be edited as ordinary application code.

## Conventions

- Import concrete modules directly; avoid broad barrel files.
- The app has no router: `app/App.tsx` directly composes feature entry screens.
- Keep state beside its owner. Use a provider only when several distant
  descendants need the same live state or actions.
- Prefer feature hooks for backend workflows and components for presentation.
  Avoid components that only forward a large callback list.
- Co-locate feature-only components, helpers, and CSS. Promote code to `shared/`
  only after it is genuinely useful across domains.
- Comments should explain non-obvious constraints, races, or ownership—not
  restate the code.
- A normal feature change should remain inside one feature directory plus its
  translation namespace whenever possible.
